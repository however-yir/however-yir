# Portfolio Governance

## 1. Commit 类型与可信度约束

为避免“活跃度包装型提交”干扰评估，统一采用以下提交类型：

- `feat:` 可验证的新功能
- `fix:` 缺陷修复（需关联问题描述）
- `refactor:` 不改变行为的结构优化
- `test:` 测试新增或修复
- `docs:` 文档更新（非运行逻辑变更）
- `chore(activity):` 仅用于仓库维护节奏，不得包含功能代码改动

## 2. `chore(activity)` 使用红线

- 仅允许修改文档、徽章、目录整理、失效链接修复。
- 不允许包含 `src/`、`main/`、`app/` 等运行代码目录改动。
- 连续两次 `chore(activity)` 后，下一次必须是 `feat/fix/refactor/test` 之一。

## 3. 设计变更留痕（ADR）

影响架构边界或关键技术选型的提交，必须补充 ADR：

- 推荐路径：`docs/adr/YYYY-MM-DD-<topic>.md`
- 最低内容：背景、决策、替代方案、影响范围、回滚策略
- PR 描述中需引用 ADR 文件路径

## 4. 招聘评审可追溯要求

- 所有 `feat/fix/refactor` 提交需在描述中包含“变更动机 + 验证方式”。
- 至少提供 1 条可复现实验命令（构建、测试或接口验证）。
- 每月归档一次核心仓库变更摘要，避免只看贡献热力图。
